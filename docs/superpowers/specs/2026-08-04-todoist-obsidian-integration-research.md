# Todoist Bidirectional Sync Research (2026)

## 1. API surface today

- **Unified API v1** (`https://api.todoist.com/api/v1/`) is the only supported surface. REST v2 and Sync v9 were deprecated Q4 2025 and shut down early 2026 — do not build on them. **All object IDs changed** in v1 (new opaque/base32-style IDs; old numeric v2/v9 IDs are invalid — there's an ID-mapping endpoint for migrating stored IDs). ([docs](https://developer.todoist.com/api/v1/), [announcement](https://groups.google.com/a/doist.com/g/todoist-api/c/LKz0K5TRQ9Q/m/IlIemN4-CAAJ), [n8n migration PR](https://github.com/n8n-io/n8n/pull/29532))
- v1 keeps both styles: RESTful CRUD endpoints (cursor-paginated) **and** the `/api/v1/sync` endpoint with `sync_token` incremental sync + batched `commands`. For a sync engine, use `/sync` exclusively.
- **Incremental sync:** first call `sync_token=*` (full sync), thereafter pass the returned token; only deltas come back. `resource_types` selects `items`, `projects`, `sections`, `labels`, `notes`, `completed_info`, etc. Deleted/completed objects arrive in deltas flagged (`is_deleted`, `checked`) — this is how deletion propagation works reliably.
- **Writes:** `commands` array, up to ~100 per request (counts as one request). Each command carries a client `uuid` (idempotency — safe retry on network failure) and `temp_id` for new objects; response returns `temp_id_mapping` (temp → real ID) and `sync_status` per-uuid (`"ok"` or error).
- **Auth:** personal API token (Bearer header, fine for a single-user desktop app) or OAuth 2.0 (new apps get refresh tokens). Personal token is the right choice here.
- **Rate limits:** ~1000 partial-sync requests / 15 min, 100 full syncs / 15 min (429 on excess). Batching keeps you far under. ([rate limits](https://developer.todoist.com/api/v1/), [stitchflow guide](https://www.stitchflow.com/user-management/todoist/api))
- **Webhooks:** exist in v1 but only activate after a user completes OAuth for an app declaring them, and require a public HTTPS endpoint — wrong fit for a sometimes-offline desktop app. **Use polling** (sync on app focus/wake + 5–10 min timer + after every local mutation). ([webhooks](https://developer.todoist.com/api/v1/))

## 2. Architecture: pull → merge → push

Sync loop (single serialized state machine, never concurrent):
1. **Push first** (drain outbox): send queued local mutations as batched commands with stored uuids/temp_ids. On `sync_status` ok, mark row synced and record temp_id→real id. Push-before-pull means the pull's returned `sync_token` already reflects your writes, avoiding echo-merge.
2. **Pull:** incremental sync with stored token; apply remote deltas.
3. **Merge/conflicts:** per-row compare. If remote changed and local row has no pending mutation → apply remote. If local has pending mutation → conflict: **field-level merge where fields differ, LWW by timestamp where the same field changed** (Todoist items carry `updated_at`). For a single-user app, LWW is acceptable; field-level (content vs due vs priority as independent fields) prevents the common "reschedule on phone wipes out edit on desktop" bug.
4. Persist new `sync_token` atomically **in the same SQLite transaction** as the applied deltas — a token saved without its data (or vice versa) is the classic corruption source.

**Semantics to get right:** completion of recurring tasks must use `item_close` (advances recurrence) not `item_update` of due date; never rewrite a recurring task's full `due` object on reschedule (destroys the recurrence string — the same bug the MCP tooling warns about). Subtasks: sync `parent_id`, create parents before children in one batch via temp_ids. Projects/sections/labels: sync as their own resource types with their own mapping rows.

## 3. Known pitfalls (from Obsidian plugins & similar)

- **Duplicate creation:** retrying a create after a timeout without idempotent uuid → duplicates. Always persist the command uuid before sending. ([ultimate-todoist-sync](https://github.com/HeroBlackInk/ultimate-todoist-sync-for-obsidian), [obsidian-todoist-plugin](https://github.com/jamiebrynes7/obsidian-todoist-plugin/releases))
- **Recurring tasks:** uncomplete/complete cycles creating duplicates or wrong next dates ([obsidian-tasks #279](https://github.com/obsidian-tasks-group/obsidian-tasks/issues/279)); treat the next-occurrence item as the *same* row (Todoist keeps the same item id across recurrences).
- **Deletion propagation:** plugins polling REST list endpoints can't see deletions (item just vanishes) → ghost tasks. Sync-token deltas with `is_deleted` solve this; tombstone locally, don't hard-delete until pushed.
- **API breakage:** plugins hardcoding v2 died in April 2025 ([eudennis fork](https://github.com/eudennis/ultimate-todoist-sync-for-obsidian-experiment)); isolate the Todoist client behind a trait.
- **Offline queue loss:** persist the outbox in SQLite, not memory ([markdoist](https://github.com/0ximst1ll/obsidoist-plugin), [Turso local-first guide](https://turso.tech/blog/building-local-first-apps-the-complete-guide-to-offline-first-database-sync)).

## 4. Recommended schema (extensible to mobile)

```sql
tasks(id TEXT PK /*local uuid*/, ..., updated_at, deleted_at /*tombstone*/)
external_links(local_id, provider 'todoist', external_id, etag_hash /*content hash of last-synced remote state*/,
               last_synced_at, remote_updated_at)
outbox(id, local_id, op /*create|update|close|delete*/, payload_json, command_uuid, temp_id, created_at, status)
sync_state(provider PK, sync_token, last_full_sync_at)
```

Content hash on `external_links` detects real remote changes vs echoes of your own push. Local UUID as canonical ID + provider mapping table keeps the store provider-agnostic; a future mobile client syncs against **your** SQLite store (e.g. Turso/embedded replica or your own outbox replication) and never talks to Todoist directly — only the desktop (or one designated agent) runs the Todoist sync loop, so there's a single writer per external provider and no cross-device Todoist races.

# Obsidian Vault ↔ Tauri App Integration Research

## 1. Integration approaches

| Approach | Works w/o Obsidian running? | Notes |
|---|---|---|
| **(a) Direct filesystem** | **Yes** — only fully reliable option | Vault = plain markdown folder. Read/write with Rust `std::fs`, watch with `notify` crate (uses FSEvents on macOS); run watcher in a background thread, emit to webview via Tauri events ([dev.to notify-rs pattern](https://dev.to/hiyoyok/file-watching-in-rust-with-notify-rs-hot-folders-for-a-sync-app-32d8)). Use `notify-debouncer-full` — editors (incl. Obsidian) do atomic write-temp-then-rename, producing multi-event bursts. |
| **(b) Local REST API plugin** | No — Obsidian must be open; desktop-only | HTTPS + self-signed cert + API key. Full CRUD, search, and uniquely **PATCH by heading/block-ref/frontmatter key**; also exposes MCP ([github.com/coddingtonbear/obsidian-local-rest-api](https://github.com/coddingtonbear/obsidian-local-rest-api)). Good as an *optional enhancement*, bad as a foundation. |
| **(c) `obsidian://` URI** | Launches Obsidian if closed | One-way fire-and-forget (open note, append via Advanced URI / Actions URI plugins); x-callback-url is opt-in and flaky/hangs in practice ([advanced-uri issue #30](https://github.com/Vinzent03/obsidian-advanced-uri/issues/30), [actions-uri](https://github.com/czottmann/obsidian-actions-uri)). Use only for "Open in Obsidian" affordance. |
| **(d) Official Obsidian CLI** (2026, [obsidian.md/cli](https://obsidian.md/cli)) | **No — "the Obsidian app must be running"** | Read/search/create/edit, daily notes, templates; symlinked at `/usr/local/bin/obsidian`. Community CLIs ([Yakitrak/notesmd-cli](https://github.com/Yakitrak/notesmd-cli), [mcky/obsidian-cli](https://github.com/mcky/obsidian-cli)) mostly wrap fs + URI, so partial offline use. |

**Conclusion:** only (a) is reliable when Obsidian is closed. (b)/(c) are optional add-ons for Obsidian-aware actions (open note, surgical PATCH while Obsidian runs).

## 2. Parsing OFM

- **Rust:** [`turbovault-parser`](https://crates.io/crates/turbovault-parser) — purpose-built: YAML frontmatter, wikilinks incl. `[[note#heading]]`, `[[note#^block]]`, embeds, tags; built on pulldown-cmark/nom. Alternative: [`obsidian-export`](https://docs.rs/obsidian-export) (lib+CLI, resolves `[[ ]]`/`![[ ]]`), or roll your own with pulldown-cmark + `gray_matter`/`serde_yaml` + regex for wikilinks. [`markdown-rs`](https://github.com/wooorm/markdown-rs) has frontmatter extension but no wikilinks.
- **JS (render side):** unified/remark ecosystem — [`remark-obsidian-md`](https://libraries.io/npm/remark-obsidian-md) (wikilinks, embeds, callouts, highlights), [`@flowershow/remark-wiki-link`](https://github.com/datopian/remark-wiki-link-plus), [Quartz's obsidian-flavored-markdown](https://github.com/quartz-community/obsidian-flavored-markdown). Recommend: parse/index in Rust, render in JS with remark plugins.

## 3. Sync & consistency

- **Change detection:** mtime alone is unreliable (1s resolution on some FSes, rsync/copy skew); store `(path, mtime, size, blake3_hash)` in SQLite — cheap mtime+size pre-check, hash to confirm ([hash-vs-mtime discussion](https://github.com/moby/moby/issues/9391), [SQLite sync-state pattern](https://dev.to/hiyoyok/using-sqlite-to-track-sync-state-in-rust-simple-reliable-zero-dependencies-53bg)).
- **Conflict avoidance:** on save, compare current file hash against hash-at-read; if diverged, three-way merge or write `note (conflict).md` — never silently overwrite. Obsidian itself has no file lock; last-writer-wins. Prefer read-mostly + append/patch-style edits to shrink the conflict window.
- **iCloud hazard:** Sonoma+ iCloud Drive uses FileProvider **dataless files** — `stat()` succeeds but `read()` triggers network fetch that can stall/fail; atomic-rename writes can miss watcher events; check `SF_DATALESS` in `st_flags` ([eclecticlight.co](https://eclecticlight.co/2023/11/21/icloud-drive-in-sonoma-fileprovider-and-eviction/), [mjtsai.com](https://mjtsai.com/blog/2023/10/27/icloud-drive-switches-to-dataless-files/)). Obsidian Sync is opaque-server-side but materializes as normal local file writes → plain fs watching works.
- **Source of truth:** **files must remain source of truth; SQLite is a disposable rebuildable index** (paths, frontmatter, links graph, tags, FTS5 body text). This is Obsidian's own metadata-cache model. App-DB-as-truth breaks the whole point (Obsidian/git/iCloud can't see it) — only app-native docs should live DB-first.

## 4. Mobile (iPhone)

Options: (1) point an iOS client at the iCloud vault — fragile (dataless files, Obsidian's special container folder, all-or-nothing sync: [forum](https://forum.obsidian.md/t/sync-vault-between-mac-and-iphone-using-icloud/106118)); (2) Obsidian Sync headless — official CLI docs mention headless E2E sync targets, but no public API for third-party clients; (3) **recommended: sync the app's own SQLite index through its existing sync layer** — Mac app is the vault gateway, pushes indexed note content (FTS + rendered metadata) to Turso/libsql embedded replicas ([Tauri+Turso pattern](https://dev.to/huakun/building-a-local-first-tauri-app-with-drizzle-orm-encryption-and-turso-sync-31pn)); iPhone gets read/search instantly, mobile edits queue as ops the Mac app replays onto files. Marco already uses Turso, so this rides existing infra.

## 5. Recommendation

**Filesystem-first, index-in-SQLite:** Rust `VaultService` = `notify` watcher (debounced 500ms) → hash-check → `turbovault-parser` → upsert SQLite tables `vault_files(path, mtime, size, hash)`, `vault_links`, `vault_tags`, FTS5 `vault_fts`. Full rescan on launch (walk + mtime/size diff) covers missed events. Edits: write file atomically w/ pre-write hash check; conflict → `.conflict` copy + UI banner. Optional tier: detect Local REST API on `127.0.0.1:27124` for heading-level PATCH while Obsidian runs; `obsidian://open` for handoff. Keep app-native docs in DB; vault notes stay files. Strongly advise vault NOT in iCloud (use Obsidian Sync or git) — or handle `SF_DATALESS` defensively. Mobile: index replicated via Turso embedded replicas; Mac = write gateway.

# Sync Architecture Research: Tauri/SQLite macOS → iPhone (Expo)

## 1. Sync layer options (state as of Aug 2026)

**Turso — two distinct products now:**
- **Embedded Replicas** (libSQL, production-stable): local file reads, writes forwarded to cloud primary, page-level replication. Works, but heavier bandwidth and writes require connectivity (write-through). https://docs.turso.tech/features/embedded-replicas/introduction
- **Turso Sync** (new Rust-rewrite engine, "Turso Database"): logical CDC-based, true local-first offline writes with explicit `push()`/`pull()`, bidirectional. Public beta since ~Mar 2025; TypeScript + Rust SDKs; Turso now recommends it over Embedded Replicas for new sync projects. Engine itself still beta. https://turso.tech/blog/turso-offline-sync-public-beta, https://turso.tech/local-first
- **React Native/Expo support exists**: official `@tursodatabase/sync-react-native` bindings (embedded DB + cloud sync), plus op-sqlite's libSQL adapter (`npx expo install @op-engineering/op-sqlite` + prebuild — needs dev client, not Expo Go). https://turso.tech/blog/react-native-bindings-for-turso, https://github.com/expo-starter/expo-opsqlite-libsql-turso
- **Pricing**: free tier ~5GB storage, 500M row reads/10M row writes per month, 100 DBs; Developer plan $4.99/mo. Trivially free for a solo app. https://turso.tech/pricing
- Conflict model is last-write-wins-ish at row level — fine for single-user multi-device.

**cr-sqlite (vlcn)**: CRDT (causal-length sets) extension for SQLite; elegant multi-writer merge. Effectively unmaintained — last npm release 0.16.3 ~2 years stale. Do not build on it in 2026. https://github.com/vlcn-io/cr-sqlite, https://www.npmjs.com/package/@vlcn.io/crsqlite

**Automerge/Yjs + SQLite**: document CRDTs, wrong shape for relational task data; you'd hand-roll persistence mapping. Only worth it for collaborative-text features. Skip.

**PowerSync**: most production-tested engine; Postgres (also MongoDB/MySQL) → client SQLite one-way stream + write-back queue via your backend endpoint. Requires running Postgres + a backend for writes = meaningful ops overhead for a solo app. Free cloud tier (2GB synced/mo, 50 connections); Pro $49/mo; Open Edition self-host free. Tauri support is via web SDK (workable, not first-class). https://powersync.com/pricing, https://docs.powersync.com/intro/self-hosting

**ElectricSQL**: pivoted to read-path Postgres sync ("shapes") + writes through your API; now best consumed via TanStack DB (0.6 added SQLite persistence, offline support, works in React Native). Good if you were Postgres-centric web-first; a re-architecture for an existing Tauri+SQLite app. https://electric-sql.com/blog/2026/03/25/tanstack-db-0.6-app-ready-with-persistence-and-includes, https://electric-sql.com/docs/stacks

**Custom sync server**: oplog table + HTTP endpoint + LWW merge. Full control, ~weeks of subtle-bug work (tombstones, clocks, migrations). Only justified if Turso Sync beta stalls.

**iCloud/CloudKit**: free, invisible auth, but CKRecord mapping from SQLite is hand-rolled, Expo access requires native modules, no Linux/server access, poor debuggability. Locks the stack to Apple. Not recommended given Expo already exists.

Comparative sanity check: PowerSync = "engineering" stable option, Electric = ambitious, cr-sqlite dormant. https://trybuildpilot.com/648-electric-sql-vs-powersync-vs-zero-2026, https://www.smashingmagazine.com/2026/05/architecture-local-first-web-development/

## 2. Third-party integrations: hub-and-spoke wins

Direct-from-each-client integration fails immediately: Obsidian vault is Mac-only filesystem; duplicate Todoist polling causes divergent snapshots + double rate-limit; secrets duplicated. Correct shape:

- **Mac app is the integration hub.** Todoist/Calendar/Obsidian sync jobs run only on the Mac, writing *into the canonical SQLite tables* (`external_tasks`, `obsidian_notes_index`, etc.). Mobile never calls third-party APIs; it just syncs the DB and sees materialized rows.
- Caveat: hub-and-spoke means mobile data is only as fresh as the Mac being awake. Mitigations: LaunchAgent periodic sync on Mac; later, move *Todoist only* (API-based) to a tiny scheduled worker (Cloudflare Worker/fly.io cron writing to Turso via HTTP API) — Obsidian stays Mac-bound regardless.
- Mobile-originated mutations to external systems (complete a Todoist task from phone): write an `outbox`/intent row locally → syncs to Turso → Mac (or worker) executes the API call and marks it done. This keeps one integration codepath and works offline.

## 3. Decisions NOW that keep mobile cheap

- **UUIDs (or ULIDs) for all PKs**, never autoincrement — multi-writer requirement #1.
- **All mutations through one repository/command layer** (single Rust or TS module), so swapping in sync push/pull or an oplog later touches one file.
- **`updated_at` + `deleted_at` (soft-delete tombstones) on every synced table**; never hard-delete.
- **Separate "core" tables from "Mac-only cache" tables** (Obsidian index, AI briefing cache) — mark which sync and which are device-local; no absolute file paths in core rows (store vault-relative paths + note IDs).
- **Store external-system IDs (`todoist_id`) as columns, sync state in an outbox table** — makes hub-and-spoke drop-in.
- **Idempotent, versioned schema migrations** shared between platforms (both clients can run them; track `schema_version`).
- Keep business logic out of Tauri Rust commands where feasible (shared TS logic reusable in Expo).

## 4. Recommendation (solo, personal)

**Turso Sync** (the new offline-writes product), since Turso is likely already in the stack: free tier covers this forever, official Expo/RN bindings exist, no server to run, conflict semantics (LWW) fine for one user. Do the §3 schema hygiene now on desktop; adopt hub-and-spoke with the Mac as integration hub + outbox for mobile-originated external mutations. Fallback if the beta engine misbehaves: stay on Embedded Replicas (stable, write-through) short-term; escape hatch is PowerSync Open Edition or a small custom oplog server — the §3 choices (UUIDs, changelog-shaped mutations, tombstones) keep all of those cheap to switch to. Avoid: cr-sqlite (dead), CloudKit (Expo friction, Apple lock-in), ElectricSQL/PowerSync (Postgres re-architecture for zero solo benefit).
