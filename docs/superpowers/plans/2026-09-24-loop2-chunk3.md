## T1 — Clickable row marks open the detail-page pickers (`loop2/c3-t1-row-marks`)

Row marks become controls that open the same pickers the task detail page uses, so a later detail redesign flows through.

Acceptance:
1. `DueDatePopover`, `LabelPicker`, the priority picker and the project picker accept a controlled `open` / `onOpenChange` (still work uncontrolled where they're used today; the detail page behaves exactly as before).
2. On a task row (Tasks, project pages, Today lists, Inbox task rows), clicking the priority bars opens the priority picker; the due badge opens the due-date picker; a label chip opens the label picker; the project name opens the project picker. The click does **not** open the task detail (stopPropagation) and does not toggle selection.
3. Choosing a value updates the task (visible on the row without reload) and closes the picker; Escape closes without change. In both cases focus returns to the row.
4. Hover state: marks show a hover affordance (hover token, pointer cursor) and have at least a 24×24px hit area, **without shifting row layout** (row stays 36px, title left edge unchanged, no reflow of the right cluster).
5. Pickers render fully inside the viewport and nothing inside them clips (at 1440×900 and 1024×700), light and dark.
6. Accessibility: each mark control has an accessible name that includes its current value (e.g. "Priority: high", "Due Aug 3", "Label quick-win", "Project Nimble"). The Tasks, Today and Inbox pages show **no new axe violations** vs baseline. Specifically, `nested-interactive` must not increase. Since the row is `role="button"` today, the builder has to restructure the row semantics (for example, the row stops being `role=button` and gets a non-widget role + keyboard handling, or the marks stay out of the tab order and are exposed some other valid way). Enter/Space on a focused row still opens the task, and j/k/x/s/f still work.
7. Completed tasks: marks still open the pickers (no product change there), strikethrough styling unchanged.

## T2 — Focused-row keys `p` · `⇧D` · `l` · `m` (`loop2/c3-t2-row-keys`, on T1)

Acceptance:
1. With a task row focused (keyboard or click-focus) on Tasks, a project page or Today: `p` opens the priority picker, `⇧D` the due-date picker, `l` the label picker, `m` the project picker.
2. The picker anchors to the row's own mark when the row has it; when the mark is missing (no due date, no labels…) it anchors to the row's right end. Either way the popup is fully visible and doesn't cover the focused row's title.
3. Picking a value or pressing Escape returns focus to the same row (the row keeps its focus ring; j/k continue from there).
4. Keys don't fire while typing in an input or editor, while any popover/dialog/menu is open, or from inside the nav trees (`rowNav.decideRowKey` guards). Inbox **note** rows keep their own `t` / `m` / `d` actions unchanged. On Inbox, task rows get `p`/`⇧D`/`l`/`m`, while `m` on a note row still means its existing action.
5. `lib/shortcuts.ts` registers the four keys (Tasks section, appended) and the `?` help panel lists them; `tests/shortcuts.test.mjs` passes and a new unit test checks the key → picker mapping and that none collides with existing keys in the same scope (`x`, `s`, `f`, `j`, `k`, Enter, `g`-prefix, ⇧F, ⇧H, `q`, digits).
6. No new axe violations on Tasks, Today and Inbox with a picker open.

## T3 — Inbox row actions overlay the row end on a fade (`loop2/c3-t3-inbox-overlay`)

Decision 7: row actions **overlay** the right end of the row on a fade: no reflow, labels and key hints kept.

Acceptance:
1. Hovering or keyboard-focusing an Inbox note row reveals its actions (with visible `RowKbd` key hints) positioned over the row's right end; the note title's width and position are **identical** before and after reveal (measure the title's bounding box: no change).
2. A fade (gradient from transparent to the row's hover background) sits behind the actions so overlapped title text doesn't collide with them; correct in light and dark mode, on the hover and focused/selected backgrounds.
3. The actions stay visible while their picker is open (existing `pickerOpen` behavior) and hide again after close / blur.
4. Every action button is reachable by Tab from the focused row, shows a focus ring, and has an accessible name; `t` / `m` / `d` keys unchanged.
5. No text clipping inside the action buttons (labels + kbd hints) at 1440 and 1024 widths. Title truncation under the overlay is the deliberate ellipsis.
6. Mixed Inbox list: task rows on Inbox also don't reflow on hover.
7. No new axe violations on Inbox.

## T4 — Deferred-commit Undo for label / capture-route / doc delete (`loop2/c3-t4-undo-delete`)

Decision (a): deferred commit via `lib/undoable.ts` `createUndoable`: hide the row, show a 5 s Undo toast, run the real delete on commit (the `ReminderCatchUp.tsx` pattern). No Rust.

Acceptance:
1. Deleting a label (Settings → Tasks & capture → Labels), a capture route (same page) or a doc (Docs tree; folders keep their current confirm flow unless trivial to include) hides it immediately and shows a sonner toast "<Thing> deleted" with an **Undo** action, for 5 s.
2. Undo restores the row in place (same position) and **no delete call reaches the DataProvider**. Letting the toast expire or dismissing it calls the real delete exactly once.
3. Deleting a second item while the first is pending commits neither early nor twice; each has its own toast.
4. Navigating away from the page while a delete is pending still commits it (no lost delete, no double delete).
5. Docs: the existing confirm dialog **stays** (dropping it is a product call left to Marco); after confirming, the doc delete is deferred behind the Undo toast like the others. Folder delete is unchanged.
6. The toast's Undo button is keyboard reachable with a focus ring, and the toast text doesn't clip.
7. Unit tests cover the commit/undo/settle-once/second-pending logic (pure helper, `node --test`). `tools/mock-tauri.js` `delete_label`, `delete_capture_route`, `delete_document` actually delete (so the browser test can observe the real delete), keeping mock field conventions.
8. No new axe violations on Settings and Docs.

## T5 — Habits: drop the hold ring (`loop2/c3-t5-habit-ring`)

Decision (b): click already logs max intensity 5; remove the hold interaction.

Acceptance:
1. `HabitCircle` (`components/goals/HabitsSection.tsx`) has no hold timer, hold state or SVG progress ring; pointer-down/up no longer start anything.
2. A click or Enter/Space on a habit circle toggles it (logs intensity 5 / unlogs) exactly as the click path does today; the checked visual is unchanged.
3. Every habit circle is keyboard reachable, shows a focus ring and has an accessible name including its state (e.g. "Morning run, done today").
4. Habits in the right rail (Habits tab, `⇧H`) and wherever else `HabitsSection` renders: no clipping, no layout shift vs before (circle size unchanged).
5. `tools/mock-tauri.js` `log_habit`/`unlog_habit` persist in-memory so the toggle is observable (the known "mock doesn't persist habit mutations" minor), without changing other mock data.
6. No new axe violations on the pages that show habits.
