## C — Subtasks on the task detail page (`loop3/c-subtasks`, stacked on B)

Marco 2026-09-24: can't reorder or multi-select subtasks in a parent's detail view; after a parent completion cascaded to all subtasks he had to reopen them one by one. Decisions: reuse the main lists' drag + selection; add a parent-reopen toast.

Code map (research): subtasks render as plain `TaskItem`s with `showGrip={false} selectable={false}` (`TaskDetailPage.tsx:511-527`); `reorder_local_tasks(ids)` already writes `position = index` for any id list (`nimble-core/src/db/tasks.rs:66`, `dp.tasks.reorder`); `useSelectionStore` is global (no list scoping); completing a parent cascades `status='complete'` to children (`task_tx.rs:527`), reopening touches only the parent (`task_tx.rs:530`).

1. **Reorder.** Subtask rows get the drag grip (same dnd-kit pattern as `SortableTaskList`); dropping persists order via `dp.tasks.reorder(subtaskIds)` and the new order survives reload/navigation. Keyboard reorder only if the main lists already have it (don't invent one).
2. **Multi-select + bulk actions.** Subtask rows are selectable exactly like main-list rows (checkbox, ⌘/shift-click range, `x`/Space conventions the main lists use), with the same bulk action bar offering at least status changes (mark as todo / complete). Selection is scoped: entering the detail page starts empty, leaving it (or opening another task) clears it, and selections never bleed into the Tasks page list or vice versa.
3. **Parent reopen toast.** Reopening a parent (any path: status dropdown, `x`, detail page) whose completion cascaded to subtasks shows one toast "Reopen N subtasks too?" with a "Reopen" action (N = subtasks completed by that cascade, i.e. still complete with `completed_at` equal to the parent's cascade timestamp; subtasks that were completed earlier are excluded). Clicking reopens exactly those; ignoring it changes nothing. No toast when N = 0. If the cascade timestamp can't be distinguished with current data, stop and report instead of guessing.
4. Standing checks (clipping, focus ring on grip/checkbox, axe on `task-detail`, before/after screenshots).

## D — Focus queue: reopening a focus-completed task restores it (`loop3/d-focus-reopen`)

Marco 2026-09-24 (reverses the absorption spec's "Do not introduce completion restore", design doc §2 line 76): if a task was completed via the Focus queue and is reopened from anywhere, it should not stay "done" in Focus. Decision: **same-day only → back at the top of Up next**, removed from the completed tray, recorded focus time kept, no timer starts; completions from earlier days stay in history only.

Code map (research): `FocusAction::Complete` (`nimble-core/src/db/focus/engine.rs:1762-1827`) sets `focus_occurrences.state='completed', completed_at, completion_reason='native'` and drops the entry from `focus_queue_state.entries_json`; task status changes route through `focus::engine::reconcile_task_effects_tx` (`tasks.rs:362` → `engine.rs:2044`), which only reacts to completions; `queue::move_to_front` exists (`focus/queue.rs:23`). Completed tray = `FocusCompletedTray.tsx` from `FocusService::history`.

1. In `reconcile_task_effects_inner_tx`, a task that changes from complete → not complete whose latest `focus_occurrences` row is `state='completed'` with `completed_at` on the **same local day** (device time zone) is restored: occurrence back to open (clear `completed_at`/`completion_reason`), a queue entry re-inserted at the top of Up next (never replacing the current/active card; no session started), queue revision bumped and the usual focus-changed event emitted so every window refreshes. Recorded session time stays attached (totals unchanged).
2. Applies to every reopen path that goes through task status changes (status dropdown, `x`, detail page, `dt`, incoming Todoist/Turso applies). Recurring tasks are unaffected (they never stay complete). Completions older than today, deleted tasks, and tasks whose occurrence was removed (not completed) don't come back. Reopening twice doesn't create duplicate entries. A task that's already in the queue again (re-added manually) isn't duplicated.
3. The completed tray no longer lists the reopened occurrence; history/`FocusTaskHistory` shows the time without a completion.
4. Tests: Rust unit/integration tests in `nimble-core` for each rule above (same-day restore, yesterday not restored, no duplicate, active card untouched, totals kept, delivery/time-comment side effects: a queued Todoist completion time-comment for that occurrence is cancelled or left per the existing delivery rules — builder reports which and why).
