## Findings (P1 first, then P2, then P3; cap 25, prefer fewer and sharper)

### P1-1 Shortcuts are not discoverable via `?` — the help panel only opens from a floating button
- Anchor: `apps/desktop/src/components/shared/HelpPanel.tsx:175-189` (only entry point is the fixed `size-9` button); `apps/desktop/src/components/layout/Dashboard.tsx:120-197` (global handler has no `?` case; `grep -rn "'?'" src` returns nothing)
- Rubric: §1.5 ("Shortcuts are discoverable via `?`")
- Screens: light `shell-help-light.png`, dark `shell-help-dark.png`
- What's wrong: The rubric's stated discovery path does not exist. The help button is a 36px circle in the corner with no label, no tooltip and no `aria-label` (measured: both `null`), so a keyboard-first user has no way to learn the shortcuts without a mouse.
- Fix: Add `?` (unmodified, `!isInput`) to the Dashboard global handler that toggles the panel, and give the button `aria-label="Keyboard shortcuts (?)"`.

### P1-2 Help panel does not close on Escape
- Anchor: `apps/desktop/src/components/shared/HelpPanel.tsx:160-170` (only a `mousedown`-outside listener; no keydown listener anywhere in the file)
- Rubric: §3.6 ("Escape doesn't return to previous state")
- Screens: light `shell-help-light.png`, dark `shell-help-dark.png`
- What's wrong: Verified in the harness: open the panel, press Escape, panel is still mounted (`stillOpenAfterEscape: true`). Every other overlay in the shell (command bar, dialog, dropdown) closes on Escape; this one silently doesn't, and the Dashboard handler's Escape case only clears selection/detail.
- Fix: In the open-effect, add a `keydown` listener that calls `closePanel()` on `Escape` (before the Dashboard handler runs — it already checks `!isInput`).

### P1-3 Nested `<button>` in the command bar result row (the Tauri-webview crash class)
- Anchor: `apps/desktop/src/components/shared/CommandBarResults.tsx:326-329` (`<DropdownMenuTrigger>` wrapping `<TooltipTrigger>`)
- Rubric: §3.3 (`<button>` inside `<TooltipTrigger>` / nested buttons)
- Screens: light `shell-commandbar-results-light.png`, dark `shell-dropdown-dark.png`
- What's wrong: Base UI renders both `Menu.Trigger` and `Tooltip.Trigger` as `<button>`. Measured DOM in the harness: `fly.querySelectorAll('button button').length === 1`, inner `data-slot="tooltip-trigger"`, outer `data-slot="dropdown-menu-trigger"`. It renders in Chromium; it is the same invalid-nesting class the project's own anti-pattern list flags for the Tauri webview.
- Fix: Compose one element: `<TooltipTrigger render={<DropdownMenuTrigger className=… />}>` (Base UI `render` prop), or put the Tooltip on a wrapping `span` — never two triggers stacked.

### P2-3 No `prefers-reduced-motion` handling in the token layer
- Anchor: `apps/desktop/src/index.css:97-108` (motion tokens) and the 12 keyframes below it (`:240`, `:255` blur+scale, `:272`, `:278-284` infinite bounce, `:404`, `:431-450` 40px fly + blur, `:479`, `:496`, `:504`, `:513`); the only guard in the codebase is `motion-reduce:` on `button.tsx:9`; harness check: 1 `reduced-motion` media rule in all stylesheets (the Tailwind utility for that one button)
- Rubric: §1.4 (restrained), §1.6 (feedback must not depend on motion); WCAG 2.3.3
- Screens: n/a
- What's wrong: The command bar flies 40px with a blur on every open, skeletons pulse, the AI stars bounce forever — none of it respects the OS setting. Because every duration routes through three tokens, the fix is one rule.
- Fix: In `index.css` `@layer base`, add
  `@media (prefers-reduced-motion: reduce) { :root { --transition-fast: 0ms; --transition-base: 0ms; --transition-slow: 0ms; } *, *::before, *::after { animation-duration: 0.01ms !important; animation-iteration-count: 1 !important; transition-duration: 0.01ms !important; } }`
  CROSS-SURFACE (Session/FocusCelebration confetti — the Session agent anchors that).

### P2-4 The focus ring is imperceptible, and three ring recipes coexist
- Anchor: `apps/desktop/src/index.css:112` (`* { @apply … outline-ring/50 }` — every non-primitive control inherits `outline: auto 1px ring/50`, measured on a focused nav button in both themes); `themes.css:27` (`--ring: oklch(0.708 0.01 60)`), `:66` (dark `0.55`); `components/ui/button.tsx:9`, `input.tsx:12`, `checkbox.tsx:11`, `select.tsx:42` … (`focus-visible:ring-3 focus-visible:ring-ring/50`, 10 files); `toggle.tsx:7`, `badge.tsx:8`, `scroll-area.tsx:20`, `tabs.tsx:59` (`ring-[3px]` spelling, plus `outline-1 outline-ring` on the last two). Zero `focus-visible:` declarations in `layout/`, `shared/`, `calendar/`.
- Rubric: §1.5 (keyboard-first — focus must be visible), §3.6
- Screens: light `shell-nav-focus-light.png`, dark `shell-nav-focus-dark.png`
- What's wrong: Measured: light `ring/50` over background = `#d8d5d2`, Lc 19.6 / WCAG 1.44; dark = `#56514e`, Lc 17.6 / 2.55.
